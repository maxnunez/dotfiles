  justify-content: flex-start | flex-end | center | space-between | space-around | space-evenly;
  align-items: stretch | flex-start | flex-end | center | baseline;
  flex-wrap: nowrap | wrap;

/* En los hijos */
.hijo {
  flex: 1;            /* crecer = 1, encoger = 1, base = 0 */
  flex: 0 0 auto;     /* no crece, no encoge, tamaño natural */
  align-self: center; /* sobreescribe align-items del padre */
  order: -1;          /* reordenar visualmente */
}

MOBILE-FIRST (hacé esto SIEMPRE)
─────────────────────────────────
/* Mobile first = base para celular, después mejorás */

/* Celular — base */
.cards { display: grid; grid-template-columns: 1fr; gap: 1rem; }

/* Tablet */
@media (min-width: 768px) {
  .cards { grid-template-columns: repeat(2, 1fr); }
}

/* Desktop */
@media (min-width: 1024px) {
  .cards { grid-template-columns: repeat(3, 1fr); }
}

Mobile-first o Desktop-first:
- Mobile-first: empezá pequeño, sumá con min-width (recomendado)
- Desktop-first: empezá grande, sacá con max-width
- Mobile-first es más fácil de mantener, Google lo prefiere

Buenas prácticas de maquetación:
- Siempre box-sizing: border-box en todo (* { box-sizing: border-box; })
- Usá rem en vez de px para tamaños de texto
- No uses px para anchos (usá %, fr, o max-width)
- Imágenes: max-width: 100% para que no desborden
- Separá contenido de estilos (no pongas style="" en HTML)

FUNCIONES
─────────
// Tradicional
function sumar(a, b) {
  return a + b;
}

// Arrow function (usá esta)
const sumar = (a, b) => a + b;

// Con cuerpo
const doble = num => num * 2;

// Sin parámetros
const hola = () => console.log("hola");

CONDICIONALES
─────────────
if (edad >= 18) {
  console.log("mayor");
} else {
  console.log("menor");
}

// Ternario (para asignaciones simples)
const msg = edad >= 18 ? "mayor" : "menor";

// AND shortcut (ejecuta solo si es true)
usuario && console.log(usuario.nombre);

// OR shortcut (valor por defecto)
const nombre = usuario.nombre || "Invitado";

// Optional chaining (no rompe si es null/undefined)
const ciudad = usuario?.direccion?.ciudad;

// Nullish coalescing (solo null/undefined, no falsy)
const total = precio ?? 0;

──────────────────────

arr.shift()              → saca del inicio
arr.includes(2)          → true/false si existe
arr.indexOf(2)           → índice del elemento

arr.map(x => x * 2)      → transforma CADA elemento (devuelve nuevo array)
arr.filter(x => x > 2)   → filtra elementos (devuelve nuevo array)

arr.reduce((acc, x) => acc + x, 0) → reduce a un solo valor

CONCEPTOS DE LÓGICA
────────────────────

Variable → Caja que guarda un valor. Cambia durante el programa.
           let nombre = "Max"; nombre = "Juan";

Condicional → Decisión. Si pasa X, hacé Y; si no, hacé Z.
           if (edad >= 18) { ... } else { ... }

Bucle → Repetir algo hasta que se cumpla una condición.
        for (let i = 0; i < 10; i++) { ... }
        while (condicion) { ... }

Operador lógico → AND (&&), OR (||), NOT (!)
        if (edad >= 18 && tieneLicencia) { ... }

Función → Bloque de código reutilizable. Entrada → proceso → salida.
        function doble(x) { return x * 2; }

Recursión → Una función que se llama a sí misma.
        function factorial(n) {
          return n <= 1 ? 1 : n * factorial(n - 1);
        }

Algoritmo → Secuencia de pasos para resolver un problema.
        Como una receta de cocina. Pasos ordenados, finitos, claros.

Complejidad → Cómo escala tu algoritmo con más datos.
        O(1) = constante (acceso a array por índice)
        O(n) = lineal (buscar en array sin ordenar)
        O(n²) = cuadrático (doble bucle anidado)
        Nunca optimices antes de tiempo. Primero que funcione.

CÓDIGO ESTRUCTURADO (programación tradicional)
──────────────────────────────────────────────
Funciones sueltas, datos separados de la lógica.
Se programa como una secuencia de instrucciones.

EJEMPLO — Sistema de usuarios ESTRUCTURADO:
───────────────────────────────────────────
$usuarios = [
  ["nombre" => "Max", "email" => "max@mail.com", "rol" => "admin"],
  ["nombre" => "Juan", "email" => "juan@mail.com", "rol" => "user"],
];

function enviarEmail($usuario, $mensaje) {
  // lógica de envío
  echo "Email enviado a " . $usuario["email"];
}

function esAdmin($usuario) {
  return $usuario["rol"] === "admin";
}

// Uso:
foreach ($usuarios as $u) {
  if (esAdmin($u)) {
    enviarEmail($u, "Bienvenido admin");
  }
}

Problemas:
  × Los datos son arrays asociativos (sin validación de estructura)
  × Si cambio "email" a "correo", explota todo
  × Código duplicado si otra parte también usa usuarios
  × Dificil de testear (todo son funciones sueltas)

────────────────────────────────────────────────────

POO — Mismo ejemplo con OBJETOS:
─────────────────────────────────
class Usuario {
  public function __construct(
    private string $nombre,
    private string $email,
    private string $rol
  ) {}

  public function esAdmin(): bool {
    return $this->rol === "admin";
  }

  public function notificar(string $mensaje): void {
    // lógica para enviar email a $this->email
    echo "Email enviado a {$this->email}";
  }
}

class Notificador {
  public function notificarAdmins(array $usuarios, string $msg): void {
    foreach ($usuarios as $usuario) {
      if ($usuario->esAdmin()) {
        $usuario->notificar($msg);
      }
    }
  }
}

// Uso:
$usuarios = [
  new Usuario("Max", "max@mail.com", "admin"),
  new Usuario("Juan", "juan@mail.com", "user"),
];
$notificador = new Notificador();
$notificador->notificarAdmins($usuarios, "Bienvenido admin");

Ventajas:
  ✓ Los datos y su comportamiento están JUNTOS
  ✓ Si cambio el email, solo toco la clase Usuario
  ✓ Cada clase tiene UNA responsabilidad (S de SOLID)
  ✓ Fácil de testear (creo un Usuario de prueba y listo)
  ✓ Reutilizable en cualquier parte del sistema

  ─ Scripts de una sola tarea (renombrar archivos)
  ─ Automatización chica
  ─ Prototipos rápidos

Usá POO para:
  ─ Apps web (Laravel, Spring Boot)
  ─ Sistemas con más de 5-10 funcionalidades
  ─ Cuando otras personas tocan el código
  ─ Cuando necesitás escalar

En la práctica, incluso en proyectos "estructurados" terminás
usando objetos. Hoy ningún framework serio usa solo funciones
sueltas.

═══════════════════════════════════════════════════
         BUENAS PRÁCTICAS (lo que esperan ver)
═══════════════════════════════════════════════════

1. Nombres claros
   ─ mal: function getData($a, $b) { }
   ─ bien: function obtenerUsuarioPorEmail(string $email): ?Usuario

2. Una responsabilidad por función/método
   ─ mal: function procesarUsuario() { valida, guarda, envía email, loggea }
   ─ bien: validarUsuario(), guardarUsuario(), notificarUsuario(), loggear()

3. No mezclar responsabilidades (separación de concerns)
   ─ El controller NO debe tener SQL
   ─ El modelo NO debe tener HTML
   ─ JS NO debe tener lógica de negocio sensible

4. Código no se repite (DRY)
   ─ Si copiaste y pegaste, creá una función

5. Validar entradas SIEMPRE
   ─ El usuario va a mandar cualquier cosa. Si es input, validalo.

6. Manejar errores
   ─ No dejes que la app explote. try/catch, mostrar mensaje amigable.

7. Escribir código como si otro lo fuera a leer
   ─ Porque va a ser así. Tu yo del futuro también es otro.

8. No optimizar antes de tiempo (YAGNI + KISS)
   ─ Primero funciona, después es correcto, después rápido.

9. Versionado (Git)
   ─ Commits chicos y frecuentes. Mensajes claros.

10. Probar el código
    ─ Manualmente al menos. Después con tests automatizados.
